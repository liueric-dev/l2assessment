     Complaints Table on Dashboard

     Context

     The Dashboard page (src/pages/DashboardPage.jsx) currently shows only
     aggregate stats (totals, category distribution, urgency breakdown) with no
     way to see or manage individual complaints. The user wants a table on the
     Dashboard listing all complaints, with per-row notes, per-row delete, and
     column sorting.

     This app is a client-only React SPA (Vite + React 19 + React Router 7,
     Tailwind, no component library) with no backend, no auth, no database —
     everything lives in localStorage['triageHistory'], written by
     src/pages/AnalyzePage.jsx when a message is analyzed. There's no existing
     "complaint" entity with a stable id or a notes field — records currently
     only have { message, category, urgency, recommendedAction, reasoning, 
     timestamp }. The closest existing UI pattern is src/pages/HistoryPage.jsx's
     expandable card list with category filter pills and a window.confirm-gated
     "Clear All" — a good style reference, but it has a latent bug (uses array
     index as React key) that should not be copied into new code, since
     sortable/filterable rows make index-as-key actively wrong.

     Decisions already confirmed with the user:
     - Reuse triageHistory records as "complaints" (no new/separate data set).
     - Notes are edited inline via an expandable row (click row → textarea →
     save on blur).
     - Add both category and urgency filter pills above the table (mirroring
     HistoryPage's pill pattern).
     - Add sortable column headers and per-row delete with a window.confirm
     step.

     Implementation

     1. New file: src/utils/complaints.js

     Centralizes data access so DashboardPage and AnalyzePage share one source
     of truth instead of duplicating localStorage logic a third time.

     - loadComplaints() — reads localStorage['triageHistory'], backfills missing
     id (via crypto.randomUUID()) and notes (default '') on any legacy record,
     writes back if it migrated anything, returns the array.
     - saveComplaints(list) — localStorage.setItem('triageHistory', 
     JSON.stringify(list)).
     - deleteComplaint(id) — re-reads, filters out the matching id, saves,
     returns new list.
     - updateComplaintNotes(id, notes) — re-reads, patches the matching record's
     notes, saves, returns new list.
     - URGENCY_RANK = { High: 3, Medium: 2, Low: 1 } and
     urgencyBadgeClass(urgency) — extracted from the duplicated inline
     badge-class logic in HistoryPage.jsx/AnalyzePage.jsx.

     2. src/pages/AnalyzePage.jsx — stamp new records at creation

     In handleAnalyze (~line 40), add id: crypto.randomUUID() and notes: '' to
     the analysisResult object literal, so new complaints don't rely on lazy
     backfill. One-line change to the object; no new imports needed for this
     file.

     3. New component: src/components/ComplaintsTable.jsx

     Props: { complaints, onUpdate } (onUpdate is called after any mutation so
     the parent can refresh).

     - State: categoryFilter, urgencyFilter (default 'all'), sortField (default
     'timestamp'), sortDir (default 'desc'), expandedId (default null).
     - Filter pills for category and urgency, styled like HistoryPage.jsx's
     existing pills (active: bg-blue-600 text-white, inactive: bg-gray-100 
     text-gray-700 hover:bg-gray-200, with counts).
     - Columns: Date/Time, Message (truncated), Category (badge), Urgency (badge
     via urgencyBadgeClass), Recommended Action (truncated), Notes indicator,
     Actions (Delete). Date/Category/Urgency are sortable via clickable <th>
     with ▲/▼ indicators; comparators: chronological Date diff for timestamp,
     localeCompare for category, URGENCY_RANK diff for urgency (not alphabetical
     — High > Medium > Low).
     - Row uses key={item.id} (not index). Clicking a row toggles an expanded
     detail <tr> (full message, full recommended action, and a <textarea 
     defaultValue={item.notes} onBlur={...}> for notes — uncontrolled +
     save-on-blur, so typing isn't disrupted by unrelated re-renders).
     - Delete button per row: window.confirm(...) → deleteComplaint(id) →
     onUpdate(...), with stopPropagation so it doesn't also toggle row
     expansion.
     - Empty states: distinguish "no complaints yet" vs "no complaints match
     filters".

     4. src/pages/DashboardPage.jsx — wire it in

     - Import loadComplaints from the new util and ComplaintsTable.
     - Add complaints state; in loadDashboardData(), replace the raw
     JSON.parse(localStorage.getItem('triageHistory') || '[]') with
     loadComplaints(), store it via setComplaints(history), and keep the rest of
     the stats/category/urgency calculations unchanged (they already operate on
     the history local variable).
     - Render <ComplaintsTable complaints={complaints} onUpdate={() => 
     loadDashboardData()} /> in a new card section after the Insights box,
     wrapped in the page's existing bg-white rounded-lg shadow p-6 container
     with an "Complaints" heading. Re-calling loadDashboardData() on update
     keeps stats/charts/table all consistent from one localStorage read, rather
     than hand-patching four pieces of derived state separately.

     Styling

     No new visual language — reuse existing Tailwind conventions already in the
     file set: card containers (bg-white rounded-lg shadow p-6), category badge
     (bg-blue-100 text-blue-800 ... rounded-full), urgency badges
     (red/yellow/green 200/900 pairs), filter pill active/inactive classes, and
     red delete-action text color family from HistoryPage's "Clear All" button.

     Critical Files

     - src/utils/complaints.js (new)
     - src/components/ComplaintsTable.jsx (new)
     - src/pages/DashboardPage.jsx (modify)
     - src/pages/AnalyzePage.jsx (modify — one-line addition)
     - src/pages/HistoryPage.jsx (reference only, not modified)

     Verification

     1. npm run dev, go to /analyze, submit a message — confirm the saved
     triageHistory record has id and notes: ''.
     2. Go to /dashboard — table renders the row; stat cards/charts still
     correct.
     3. Manually seed a legacy record (no id/notes) into
     localStorage['triageHistory'] via devtools, reload /dashboard — confirm it

     4. Click a row, type notes, click away (blur), reload — notes persisted.
     5. Click Date/Category/Urgency headers — sort toggles asc/desc correctly
     (chronological, alphabetical, severity-ranked respectively).
     6. Apply category + urgency filters together — confirm AND semantics.
     7. Delete a row — confirm dialog, row removed, stats/charts recompute, no
     other row affected.
     8. Delete all rows — verify empty state and zeroed stats/charts.

     Batch Message Analysis on AnalyzePage

     Context

     Today src/pages/AnalyzePage.jsx only analyzes one customer message at a
     time: it calls categorizeMessage() (src/utils/llmHelper.js), computes
     urgency/recommended action, shows one detailed result card, and appends the
     single result to triageHistory in localStorage.

     The user wants to triage multiple messages in one pass. This adds:
     1. A toggle between "Single message" (plain text) and "Batch" (JSON array
     of strings) input modes.
     2. Client-side validation that only enables the Analyze button in batch
     mode once the textarea contains valid JSON that parses to an array of
     strings.
     3. A results view that scales to many results: paginated 10-per-page, with
     more compact rows than the current full detail card.

     No existing toggle, pagination, or user-input JSON-validation pattern
     exists anywhere in the codebase (confirmed via exploration), so these are
     built fresh, following the visual conventions already used (pill-style
     buttons, expandable rows like ComplaintsTable.jsx and HistoryPage.jsx, the
     existing animate-spin loading pattern).

     Design decisions

     - Unify the results view. Rather than keeping the current single-result
     detail card for single-message mode and building a separate compact table
     just for batch, results becomes an array in both modes (a single analysis
     just produces an array of length 1). This keeps one code path and matches
     the user's request to make "analysis results" paginated/compact generally.
     - Sequential processing with progress. Batch messages are analyzed one at a
     time in a loop (not Promise.all), so we can show "Analyzing 3 of 12..."
     reusing the existing spinner button pattern, and to avoid hammering the
     Groq API concurrently. categorizeMessage() already internally falls back to
     a mock on API failure and does not throw, so no per-item try/catch is
     needed.
     - Switching input mode clears the textarea and results. Avoids confusing
     carry-over of text that's invalid in the new mode.
     - New AnalysisResultsTable component
     (src/components/AnalysisResultsTable.jsx) handles compact rows + pagination
     + expand-for-detail, mirroring the expandable-row pattern already in
     ComplaintsTable.jsx. This keeps AnalyzePage.jsx focused on
     input/orchestration.
